# ADR-016 — Backend-Authoritative Prescription & Scheduled Opportunity Integrity

Status: Accepted — CURRENT
Date: 2026-08-31 (Phase 10); extended 2026-08-31 (Phases 10B and 10C)
Supersedes: nothing (extends ADR-015's trust-boundary model to two gaps it left open; Phase 10B closes this ADR's own Phase 10 "Known limitation")

## Context

ADR-015 established that `authorizeWorkoutLifecycleMutation` is the single point where a lifecycle mutation is authorized, issuing a short-lived, single-use, single-operation grant that Firestore Rules require before a critical write commits. Two gaps survived that design:

1. **Prescription content authority.** `workoutPrograms/{programId}` (create) and `workoutProgramState/active` (create/update) — the two writes that actually make a plan *live* — never required a grant at all. They were validated only by `workoutProgramCommonValid`/`workoutProgramLimitationValid`: structural shape and metadata consistency, never a cross-check of individual `sessions[].exercises[].exerciseId` against the exercise catalog's real `limitationProfile`. A client that called `authorizeWorkoutLifecycleMutation` and omitted the optional `targetProgramSource` field skipped `sealTargetProgram` (and therefore `assertPlanSafe`) entirely; a client that never called the callable at all could write directly to these two collections and pass every Rules check with a structurally-plausible but semantically unsafe or absurd plan (an exercise incompatible with a declared limitation, or an exercise with 1,000,000 sets).
2. **Scheduled opportunity authority.** `execution.sessionIndex` (100% client-supplied) was used, on both client and backend, as the sole selector for "which prescribed session is this evidence graded against." The "expected index" parameter that existed in the qualification function's signature was always fed the execution's own `sessionIndex` at the only real call site, making the check tautological. No code path independently derived which session a given calendar date actually owed from the real rotation.

## Decision

### Prescription content

- `sealTargetProgram` runs **unconditionally** for every operation that installs prescription content (`INITIALIZE`, `MIGRATE`, `ACTIVATE`, `ADAPT`) — the client can no longer opt out of the safety check by omitting `targetProgramSource`.
- `assertPlanSafe` gained numeric bounds (sets 1–10, rest 0–600s, reps a bounded string) as defense-in-depth against a structurally-plausible-but-absurd plan, in addition to its existing exercise-active/limitation-compatibility checks. Bounds are explicitly *not* the primary mechanism — see "Known limitation" below.
- `firestore.rules`' `workoutPrograms/{programId}` `create` rule now requires, whenever the resulting `workoutProgramState/active` carries a `programInstanceId` (i.e. a V2/lifecycle-managed program): a valid, same-user, unexpired, unconsumed grant for one of `INITIALIZE`/`MIGRATE`/`ACTIVATE`/`ADAPT`/`RECOVER` whose `targetContentIdentity` equals the `programId` being written. Legacy V1 (no `programInstanceId` on the active pointer) is unaffected — that write path predates the lifecycle authority model and is out of this phase's scope.
- `workoutProgramState/active`'s own Rules already required `getAfter(workoutPrograms/{programId}).data.status == 'active'`, so once `workoutPrograms/{programId}` create is grant-gated, `workoutProgramState/active` is transitively protected without a separate check.

**Why `RECOVER` is included.** `RECOVER` is used by the client's automatic-progression/reconciliation path (`src/services/workoutPrograms.ts`) even when installing genuinely new prescription content; its backend validation reconciles identity/state consistency but does not itself call `assertPlanSafe`. Excluding it broke that legitimate flow (`workoutProgression.integration.test.ts`, discovered during this phase's regression run). Including it still requires the write to have gone through the authority callable at all — closing the literal reported exploit ("a modified client... obtained backend authorization... sealed via Admin SDK" without the intended validation ever running) — even though `RECOVER` itself does not independently re-verify plan safety. See "Known limitation."

### Content identity binding

- The grant is bound to `targetContentIdentity` (and, for the scheduled-opportunity operations below, to`targetNextSessionIndex`/`targetCursorDate`/`targetScheduleEvents`), all backend-derived or backend-computed, never client-authored content. A modified client cannot swap the plan content after authorization without also changing the identity the grant is bound to, which would then fail the identity-match check.

### Scheduled opportunity integrity

- **The schedule decides which session was expected — never the execution.** `functions/src/workoutLifecycle/authorizeMutation.ts`'s `COMPLETE_SCHEDULE` handler now loads the account's authoritative schedule context (program's session count, schedule config's training days, the ProgramInstance's real activation date, and the current `scheduleState` cursor) and calls the exact same pure resolver the client uses (`resolveWorkoutSchedule`, synced from `src/scheduleEngine/resolver.ts` into `functions/src/workoutLifecycle/scheduleEngine/` — see "Shared resolver" below) to compute what session was really owed for the given date. It only issues a grant if `request.sessionIndex` equals that computed value and a matching finished execution exists. `execution.sessionIndex` is never used to select its own expectation.
- **A new `RESOLVE_MISSED_SESSION` operation** does the equivalent for the miss-decision flow (`CONTINUE_SEQUENCE` / `FOLLOW_SCHEDULE`), using `detectMissedSessionGap` against the authoritative cursor — never trusting the stored `pendingMissDecision` payload's own `missedSessionIndex`/`calendarSessionIndex` values, which a client could otherwise forge via the (necessarily ungated, see below) miss-*detection* write.
- **`scheduleState` writes for V2 programs are grant-bound whenever they change the rotation position.** A write that leaves `nextSessionIndex`/`cursorDate` unchanged (recording a newly-detected `pendingMissDecision`, or other bookkeeping) stays ungated — that preserves the existing miss-detection UX exactly as it worked before. A write that *advances* the rotation must match `targetNextSessionIndex`/`targetCursorDate` on a valid `COMPLETE_SCHEDULE` or `RESOLVE_MISSED_SESSION` grant. This closes the "client pre-positions the cursor to a favorable value" variant of the same exploit.
- **Backdating grace window.** `COMPLETE_SCHEDULE` and `RESOLVE_MISSED_SESSION` reject a `scheduledLocalDate` more than 3 days before the server's current date (offline-sync slack) or in the future. This is a deliberate compromise, not exact wall-clock enforcement — the product allows a session to be logged a day or two late after being offline; it does not allow fabricating adherence for a date long past.

### Shared resolver, not a reimplementation

`src/scheduleEngine/{calendar,resolver,types,localDate}.ts` are pure, dependency-free TypeScript except for the `Weekday` type import from the RN-only `AppState.tsx`. `scripts/syncScheduleEngineToFunctions.cjs` copies them into a generated, gitignored `functions/src/workoutLifecycle/scheduleEngine/` directory (with a hand-written `weekday.ts` shim replacing the one non-portable import) as a `prebuild`/`pretypecheck`/`pretest` step in `functions/package.json`. `src/scheduleEngine/` remains the single source of truth. This guarantees the backend's notion of "what session is expected" can never drift from the client's — it is the same code, not a parallel reimplementation that could diverge.

The client's own optimistic adherence display (`src/progressionEngineV2/prescribedOpportunities.ts`) was fixed the same way conceptually but with a smaller, purpose-built replay (`src/progressionEngineV2/expectedSessionIndex.ts`): it folds over the already-authoritative (grant-protected) `COMPLETED`/`SKIPPED` ledger for a `ProgramInstance` to derive the true expected index per date, rather than re-deriving the full rotation/miss-decision state machine client-side. It only needs to *agree with history the backend already accepted*, not re-derive the anchor/miss-decision machinery itself.

## Phase 10B addendum — backend canonical prescription generation

Phase 10's "Known limitation" (full backend-independent regeneration was scoped out as a "materially larger effort") turned out to be smaller than estimated once actually investigated: `src/workoutPrescription/`'s deterministic pipeline is ~3,320 pure-candidate lines with **zero** RN/Expo/Firebase imports and **zero** randomness anywhere in the pipeline (verified by grep — the only `Date.now()` calls are pure telemetry timing in an excluded React hook). Its only non-portable dependency is a value-level import of `WEEKDAY_ORDER`/`defaultQuiz`/`Quiz` from the RN-adjacent (but itself RN-free) `src/state/AppState.tsx`.

### Shared engine, not a reimplementation

`scripts/syncPrescriptionEngineToFunctions.cjs` (same pattern as `syncScheduleEngineToFunctions.cjs`) mirrors the exact `src/` directory layout for the engine's dependency closure — `workoutPrescription/`, `data/exercisesSeedData.ts`, `types/exercise.ts`, `lib/questionnaireSchema.ts`, `onboarding/steps.ts`, `workoutLifecycle/types.ts` (the client one), `prescriptionEvolution/{config,cycleEvolution,equivalence,levelPromotion}.ts`, and the two JSON template/limitation catalogs — into a generated, gitignored `functions/src/workoutLifecycle/prescriptionEngine/` (and a sibling `functions/src/workoutLifecycle/docs/` for the JSON files, since `resolveJsonModule` needs them physically present). Mirroring the real tree means every existing relative import resolves unchanged — no per-file import rewriting needed, except one dependency: `state/AppState.ts` is **mechanically sliced** (not hand-written) from the real `AppState.tsx`'s pure type/const prefix (`Sex` through `Quiz`, plus `defaultQuiz`, skipping the React-Context/`TabId` section) by the same sync script, so the large `Quiz` type surface can never silently drift the way a hand-maintained shim could. `src/workoutPrescription/` and `src/prescriptionEvolution/` remain the single source of truth.

### Backend context loader

`functions/src/workoutLifecycle/prescriptionContext.ts` reads the same authoritative Firestore collections the client reads — all 116 `exercises/*` docs (`EXPECTED_EXERCISE_COUNT`, mirroring `isExerciseCatalogDocument`/`loadExerciseCatalogForLimitations`), the live `workoutTemplates/{id}` doc for whatever template `selectTemplate(answers)` deterministically picks (converted via the already-shared `fromWorkoutTemplateDocument`), and `limitationDatasetState/active`'s identity (hash-verified via `canonicalizeLimitationProfiles` + `node:crypto`, the Admin SDK equivalent of the client's `expo-crypto` call) — never from anything the client submitted.

### Canonical generation per operation

- **INITIALIZE / MIGRATE / ADAPT**: `generateCanonicalPlan` calls the full `generateWorkoutPrescription(answers, context)` against authoritative answers (the questionnaire's own persisted `answers` for INITIALIZE/MIGRATE; `assertSnapshot`'s already-computed `expectedInputs` for ADAPT) and the live catalogs above. The result — not the client's `targetPlan` — is what `sealTargetProgram` seals; `assertPlanSafe` still runs on it as a self-check.
- **PREPARE**: branches on the now-*proven* (persisted-event-checked) `earnedFact.type`. `LEVEL_PROMOTION` reuses the same full-engine path — `assertSnapshot`'s `expectedInputs` already pins `days`/`trainingDays` to the *current* active prescription's values (it spreads `sourceInputs` before overriding only `level`), which is exactly what the client's separate `buildLevelPromotionAnswers` helper exists to guarantee — so no separate porting of that helper was needed. `CYCLE_EVOLUTION`/`MOTIVATIONAL_RENEWAL` use a new `generateCanonicalCycleEvolution`, mirroring `src/services/prescriptionEvolution.ts`'s conservative transformer exactly: it starts from the *current* sealed sessions (never re-selects a template), builds the equivalence catalog from the same bundled `EXERCISES_SEED` the client uses for this specific path (not the live Firestore catalog — this mirrors existing client behavior byte-for-byte rather than "improving" it, which would be its own separate change), walks the `previousProgramInstanceId` chain for the anti-ping-pong window, and calls the shared `evolveCycle`.
- **ACTIVATE**: unchanged — it already only re-seals whatever `PREPARE` put in `pendingEvolutions.plan` (byte-equality checked), so fixing `PREPARE` was sufficient.
- **RECOVER**: closes the Phase 10 P2. Traced end-to-end: the V1 legacy rotation's `automatic_progression` path routes a **freshly, genuinely generated** client plan through `RECOVER` (not stale/already-sealed content, as ADR-016's Phase 10 text assumed) — `RECOVER` is the first and only time that content is validated at all. `RECOVER` still never calls `sealTargetProgram` (it remains identity/state reconciliation only, per its docs), but it now runs `assertPlanSafe` on `request.targetPlan` whenever one is present, closing the "zero validation of any kind" gap without touching V1's own separate legacy rotation-generation logic (out of scope — a distinct system predating V2).

### Design choice: backend-generated is authoritative, never diffed against the client

The backend always computes its own canonical plan and seals *that*, regardless of what the client's `targetPlan` contains — the client's copy is treated as an optimistic-UI value only, never compared byte-for-byte against the backend's. This was the explicitly preferred design (over building a canonical-equality diffing layer) because it doesn't need the two independent computations to agree at all for the *security* property to hold: only one computation is ever authoritative.

### Verification

`functions/src/workoutLifecycle/__tests__/realCatalogFixture.ts` seeds the *actual* bundled catalog (all 116 exercises via `loadLocalLimitationDataset()`, the full T001-T090 template library) into the Firestore Emulator, so `authorizeMutation.integration.test.ts` exercises genuine canonical generation — not synthetic 2-exercise fixtures. Its "safe-but-wrong" acceptance test submits a structurally valid, in-bounds, real-exercise ADAPT candidate for an account with a declared knee limitation, and independently verifies every exercise in the *sealed* plan against its real Firestore `limitationProfile` (never `status: 'avoid'` for the declared region) — proving the client's candidate is never what actually gets installed, not merely that an unsafe candidate is rejected. A parallel test proves a 1,000,000-set client candidate never appears in sealed content. LEVEL_PROMOTION and CYCLE_EVOLUTION each have a dedicated test proving canonical generation runs and template/split/frequency are preserved for the latter.

## Phase 10C addendum — canonical response client integration

Every client path that persists newly generated authoritative content now consumes the complete `result.canonical` response rather than its pre-authorization candidate. `saveAndActivateWorkoutProgram` uses the canonical plan, prescription identity, content identity, and template metadata for `workoutPrograms`, `ProgramInstance`, lifecycle state, and the active pointer. `prepareEvolutionAttempt` stores those same canonical fields in `pendingEvolutions/current`. The direct legacy MIGRATE bootstrap also installs and points lifecycle state at the backend-sealed canonical program when catalog drift makes it differ from the legacy candidate.

The backend now computes `targetContentIdentity` with the same `wpg_*` identity shape used by the client; it is no longer conflated with `planId`. INITIALIZE/MIGRATE and content-changing ADAPT bindings are recomputed from that canonical identity, so ProgramInstance/cycle/event bindings cannot retain a candidate-derived suffix during a catalog race. The client checks that canonical `targetPrescriptionIdentity` equals `targetPlan.planId` and, on save/PREPARE paths, independently recomputes the expected `wpg_*` identity before writing.

Canonical-generating operations (`INITIALIZE`, `MIGRATE`, `ADAPT`, `PREPARE`) fail closed when the response omits canonical content. The authority provider JSON-clones the response before returning it, preventing a local candidate alias or post-response mutation from changing the object later used for persistence. ACTIVATE continues to consume the already-canonical pending content; RECOVER remains reconciliation and is not forced into a nonexistent generation contract.

`RECOVER`'s content check remains narrower than full canonical generation by design: it validates bounds/catalog/limitations via `assertPlanSafe` but does not independently regenerate or diff the V1 legacy rotation system's own output, since that system predates and is architecturally separate from the V2 engine this ADR governs.
